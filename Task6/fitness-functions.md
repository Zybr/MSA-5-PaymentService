# Задание 6. Fitness-функции платёжной системы

| Название функции              | Назначение                                                             | Что проверяется                                                                                                                                                     | Действие при нарушении                                                                                                                     | Способ реализации                                                                                                                                        |
|-------------------------------|------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|
| `PaymentDataConsistency`      | Проверка консистентности данных о платеже между сервисами              | Статус, сумма, валюта, `paymentId`, `operationId` и внешний идентификатор операции совпадают в `Payment Service`, оркестраторе, платёжном шлюзе и хранилище событий | Заблокировать дальнейшую обработку платежа, создать инцидент для SRE и запустить задачу сверки данных                                      | Scheduled job, который сравнивает записи в PostgreSQL, события из outbox/event log и состояние процесса в Camunda/Zeebe                                  |
| `SagaStateConsistency`        | Контроль корректности состояния Saga-оркестрации                       | У каждого активного экземпляра Saga есть допустимое состояние из state machine; невозможны переходы в обход списания, проверок или компенсации                      | Перевести Saga в безопасное состояние `FAILED` или `REFUND_PENDING`, отправить алерт и записать причину в audit log                        | ArchUnit-тесты для запрета обхода оркестратора и интеграционный тест, сверяющий статусы с таблицей переходов из `Task2`                                  |
| `NoMoneyStuckBetweenSystems`  | Предотвращение зависания денег между списанием и финальным результатом | Если списание выполнено, то платёж должен завершиться зачислением контрагенту, возвратом клиенту или находиться в допустимом ожидании ручной проверки/cut-off       | Автоматически инициировать возврат, если нет допустимого ожидания; уведомить клиента и команду поддержки                                   | Cron job по таблице платежей и истории операций: ищет платежи после `DEBIT_SUCCEEDED` без `CREDIT_SUCCEEDED` или `REFUND_SUCCEEDED` дольше заданного SLA |
| `HangingProcessDetector`      | Выявление зависших экземпляров BPMN-процесса                           | Процесс не находится в одной технической задаче дольше разрешённого времени; активные job в Zeebe имеют живые retries и worker heartbeat                            | Создать incident в Camunda/Operate, отправить алерт SRE, при необходимости повторно активировать job или запустить компенсацию             | Мониторинг Zeebe/Operate API и метрик Prometheus по длительности активных элементов процесса                                                             |
| `ManualReviewDeadlineControl` | Контроль дедлайна ручной антифрод-проверки                             | Платёж в состоянии `MANUAL_REVIEW_PENDING` не ожидает решения оператора дольше 20 минут                                                                             | Завершить ожидание по cut-off правилу, по умолчанию разрешить платёж и записать событие `CUT_OFF_EXPIRED`                                  | BPMN timer boundary/event-based gateway и отдельная scheduled-проверка платежей со статусом ручной проверки                                              |
| `ExternalCheckTimeoutControl` | Контроль таймаутов внешних проверок                                    | Антифрод, compliance и limits-проверки отвечают в пределах заданного таймаута; retry не превышает лимит попыток                                                     | Остановить ожидание ответа, применить безопасное бизнес-правило: отказ или переход в ручную проверку; отправить алерт владельцу интеграции | Resilience4j timeout/retry policy, метрики latency/error rate и интеграционные тесты с Testcontainers/WireMock                                           |
| `CompensationCompleteness`    | Проверка полноты компенсационных транзакций                            | Для каждого отказа после успешного списания есть успешный возврат; для подозрительных операций также есть уведомление безопасности                                  | Повторить возврат идемпотентно; если повтор неуспешен — открыть критический инцидент и заблокировать платёж                                | Scheduled reconciliation job по событиям `*_DENIED`, `CREDIT_FAILED`, `REFUND_SUCCEEDED`, `SECURITY_NOTIFIED`                                            |
| `IdempotencyGuard`            | Защита от повторного выполнения финансовых операций                    | Списание, возврат и зачисление не выполняются повторно при retry, повторном сообщении или перезапуске worker                                                        | Отклонить дублирующую команду, вернуть ранее сохранённый результат и записать предупреждение в audit log                                   | Уникальные ключи по `operationId` в PostgreSQL, idempotency-key во внешних API и контрактные тесты повторной отправки команд                             |
| `FinalStateCompleteness`      | Проверка, что каждый платёж приходит в корректное конечное состояние   | В течение SLA платёж завершается одним из конечных статусов: `COMPLETED`, `FAILED` или `REFUNDED`; незавершённые статусы не остаются навсегда                       | Отправить алерт, перевести платёж в разбор или автоматически запустить компенсацию по последнему стабильному состоянию                     | Periodic health check по таблице платежей и Zeebe process instances с порогами времени для каждого промежуточного статуса                                |
| `NotificationDeliveryControl` | Контроль обязательных уведомлений по итогам Saga                       | Клиент получает уведомление об успешном платеже, отказе или возврате; служба безопасности получает уведомление по fraud/manual deny                                 | Повторить отправку уведомления через outbox; после исчерпания попыток создать incident для поддержки                                       | Outbox pattern, dead-letter queue, метрики доставки сообщений и consumer lag в брокере событий                                                           |
| `AuditTrailCompleteness`      | Обеспечение трассируемости и расследуемости платежа                    | Для каждого значимого шага Saga записано событие с временем, причиной перехода, correlation id и участником операции                                                | Запретить закрытие платежа без полного audit trail, отправить предупреждение в систему мониторинга                                         | Проверка audit log/event log в CI и scheduled job, который ищет платежи с пропущенными событиями                                                         |
| `SagaArchitectureRules`       | Автоматический контроль архитектурных ограничений Saga                 | Доменные сервисы не управляют процессом напрямую; оркестрация сосредоточена в Payment Orchestrator; внешние вызовы проходят через адаптеры                          | Завалить сборку и не допустить merge в основную ветку                                                                                      | ArchUnit-тесты в CI, проверяющие зависимости пакетов, запрет прямых вызовов BPMN из API и соблюдение слоёв архитектуры                                   |
